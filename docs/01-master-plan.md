# خطة مشروع منصة B2B للمستوردين والمصدّرين
### وثيقة التخطيط الرئيسية — الإصدار 1.0

---

## 1. الملخص التنفيذي

منصة تجارة إلكترونية بين الشركات (B2B Marketplace) تربط **الموردين/المصدّرين** بـ **المشترين/المستوردين** في بيئة واحدة تغطي دورة العمل الكاملة:

> اكتشاف المنتج → طلب عرض سعر (RFQ) → التفاوض → أمر الشراء (PO) → الفاتورة → الدفع → الشحن → التقييم → **القيد المحاسبي الآلي**

الفارق الجوهري عن العرض الأولي: إضافة **نظام محاسبي متكامل بالقيد المزدوج** يعمل على مستويين:
1. **محاسبة المنصة (Super Admin):** دفتر أستاذ للمنصة نفسها — العمولات، الاشتراكات، الذمم على الموردين، التسويات، المصاريف التشغيلية، القوائم المالية.
2. **محاسبة المورد (Supplier Accounting):** دفتر أستاذ مستقل ومعزول لكل مورد — مبيعاته، مشترياته، مخزونه، عملائه، ضرائبه، أرباحه، قوائمه المالية.

هذا يحوّل المنصة من "سوق إلكتروني" إلى **نظام تشغيل تجاري (Commerce OS)** — وهو ما يرفع قيمة الاشتراك ويقلّل معدل مغادرة الموردين (Churn) بشكل حاد، لأن المورد الذي أصبح دفتره المحاسبي داخل المنصة لا يغادرها بسهولة.

---

### 1.1 مواءمة المصطلحات

| في وصف المشروع | في النظام | الدور التقني |
|---|---|---|
| المستورد / المصدّر | **المورد (Supplier)** | البائع: ينشر منتجاته، يستقبل الطلبات، يرسل عروض الأسعار |
| تاجر الجملة | **المشتري (Buyer)** | يتصفّح، يتواصل، يطلب عرض سعر، يشتري |
| الصنف (قطع سيارات، منزليات، أثاث، هدايا وألعاب…) | **الفئة (Category)** | شجرة تصنيف + تخصّص المورد بها |
| طلب عرض سعر | **RFQ** | طلب مفتوح أو موجّه |
| عرض السعر المُرسَل | **Quotation** | عرض برقم وتاريخ صلاحية |
| الاتفاق النهائي | **Order / PO** | أمر شراء مولّد من العرض المقبول |

> كل ما ورد في هذه الوثائق بلفظ "المورد" ينطبق حرفياً على "المستورد" في السوق السوري، و"المشتري" على "تاجر الجملة".

## 2. نطاق المشروع

### 2.1 داخل النطاق (In Scope)

| المجال | الوحدات |
|---|---|
| السوق | الكتالوج، البحث والتصنيف، صفحات الموردين، المقارنة |
| التفاوض | RFQ، عروض الأسعار المتعددة، التفاوض، القبول |
| العمليات | أوامر الشراء، العقود، الشحن، التتبع، الاستلام |
| المالية | الفواتير، المدفوعات، العمولات، التسويات، المحفظة |
| **المحاسبة** | **دليل الحسابات، اليومية، الأستاذ، AR/AP، المخزون، الضرائب، القوائم المالية، الإقفال** |
| التواصل | محادثة فورية، مرفقات، إشعارات متعددة القنوات |
| الإدارة | لوحة Super Admin، إدارة المستخدمين، الصلاحيات، التقارير، إدارة المحتوى |
| التطبيقات | ويب متجاوب + تطبيق جوال (React Native) |

### 2.2 خارج النطاق — المرحلة الأولى (Out of Scope v1)

- التخليص الجمركي الآلي والربط مع أنظمة الموانئ.
- التمويل التجاري (Trade Finance / LC / Factoring) — مؤجّل للمرحلة 3.
- الربط مع أنظمة ERP خارجية (SAP/Odoo) — يُكتفى بـ API عام + تصدير قياسي.
- الذكاء الاصطناعي للتسعير التنبؤي — مؤجّل.

## 3. الأدوار والصلاحيات (RBAC)

النظام يعتمد **صلاحيات دقيقة (Granular Permissions)** مجمّعة في أدوار قابلة للتخصيص، مع عزل بيانات على مستوى المستأجر (Tenant Isolation).

### 3.1 مستوى المنصة

| الدور | الوصف |
|---|---|
| **Super Admin** | صلاحية كاملة، بما فيها محاسبة المنصة والإقفال المالي |
| **Platform Accountant** | محاسب المنصة: القيود، التسويات، التقارير — بدون صلاحيات تقنية |
| **Operations Manager** | اعتماد الموردين، مراجعة النزاعات، إدارة الطلبات |
| **Support Agent** | دعم فني، عرض فقط للبيانات المالية |
| **Content Manager** | التصنيفات، البانرات، المدونة، صفحات SEO |

### 3.2 مستوى المورد (كل مورد = مستأجر مستقل)

| الدور | الوصف |
|---|---|
| **Supplier Owner** | مالك الحساب، صلاحية كاملة داخل مستأجره |
| **Supplier Accountant** | وحدة المحاسبة فقط: الفواتير، القيود، التقارير |
| **Sales Manager** | عروض الأسعار، الطلبات، العملاء |
| **Inventory Keeper** | المخزون، المستودعات، حركات الصنف |
| **Viewer** | عرض فقط |

### 3.3 مستوى المشتري

| الدور | الوصف |
|---|---|
| **Buyer Owner** | الحساب والاعتمادات المالية |
| **Procurement Officer** | إنشاء RFQ وأوامر الشراء ضمن سقف صلاحية |
| **Approver** | اعتماد أوامر الشراء فوق سقف محدد (Approval Workflow) |

> **قاعدة تصميم:** كل استعلام على بيانات المورد يمرّ عبر Global Scope إلزامي على `tenant_id`، ولا يُسمح بأي استعلام محاسبي بدون نطاق مستأجر صريح.

## 4. الوحدات الوظيفية

### 4.1 وحدة الموردين / المستوردين (Supplier Module)
- التسجيل متعدد الخطوات + **التحقق (KYB)**: السجل التجاري، البطاقة الضريبية، شهادة التصدير.
- **اختيار الأصناف التي يعمل بها** (فئة رئيسية + فئات فرعية + الماركات/الوكالات) — خطوة إلزامية في التسجيل، وهي التي تُدرج المستورد في دليل الفئة وتجعله يتلقى طلبات عروض الأسعار الخاصة بها.
- إدخال المنتجات التي يستوردها: يدوياً، أو استيراد جماعي من ملف Excel/CSV بقالب جاهز.
- حالات الحساب: `pending → under_review → verified → suspended`.
- الملف العام: الشعار، الوصف، الشهادات، الأسواق المستهدفة، الحد الأدنى للطلب (MOQ)، شروط الدفع الافتراضية.
- شارات الثقة (Verified / Gold / Premium) مرتبطة بخطة الاشتراك.

### 4.2 وحدة الكتالوج
- منتج بخصائص B2B: **تسعير تدرّجي (Tiered Pricing)** حسب الكمية، MOQ، وحدة القياس، زمن التجهيز (Lead Time)، بلد المنشأ، كود HS.
- متغيّرات المنتج (المقاس/اللون/الدرجة) مع SKU مستقل لكل متغيّر.
- أسعار مخفية اختيارياً ("اطلب عرض سعر").
- قوائم أسعار خاصة لكل عميل (Customer Price Lists).

### 4.3 وحدة RFQ ودورة التفاوض
```
المشتري ينشئ RFQ ──> يُرسل لعدة موردين (أو عام)
        │
        ├─> المورد يقدّم عرض سعر (Quotation) برقم وتاريخ صلاحية
        ├─> تفاوض (Counter-Offer) مع سجل كامل للنسخ
        └─> المشتري يقارن العروض في جدول موحّد ──> يقبل عرضاً
                                                      │
                                       يتحوّل العرض آلياً إلى أمر شراء (PO)
```
**مساران للمشتري — كلاهما مدعوم:**

| المسار | الوصف | التنفيذ |
|---|---|---|
| **أ. البحث المباشر** | تاجر الجملة يدخل فئة "قطع سيارات" ⟵ يرى **دليل المستوردين** المسجّلين فيها ⟵ يفتح ملف مستورد ⟵ يتصفّح منتجاته ⟵ يراسله مباشرة أو يرسل له طلباً | دليل مبني على جدول `supplier_categories` + محادثة مرتبطة بسياق |
| **ب. طلب عرض سعر مفتوح** | تاجر الجملة ينشر طلباً لمنتج معيّن دون اختيار مستورد ⟵ **يصل إشعار لكل المستوردين المسجّلين في فئة المنتج** ⟵ كل من يرغب يرسل عرض سعر ⟵ المشتري يقارن ويختار | بث آلي عبر `rfq_invitations` بمصدر `broadcast` |

**قواعد البث الآلي للطلب المفتوح:**
- الاستهداف بالفئة أولاً، ثم فلترة اختيارية بالمحافظة/المدينة أو بالحد الأدنى للطلب.
- القنوات: إشعار داخل التطبيق + Push + بريد (وSMS/WhatsApp للطلبات عالية القيمة).
- سقف يومي لعدد الطلبات المُرسَلة للمستورد الواحد لمنع الإزعاج، مع تفضيلات إشعار قابلة للضبط.
- المشتري يرى عدّاداً حيّاً: *"وصل الطلب إلى 14 مستورداً · فتحه 9 · قدّم عرضاً 4"*.
- إمكانية إخفاء هوية المشتري حتى قبول العرض (اختياري).

**باقي الدورة:**
- مقارنة آلية: السعر، مدة التسليم، شروط الدفع، تقييم المورد، التكلفة الإجمالية شاملة الشحن.
- إغلاق تلقائي للعروض منتهية الصلاحية.

### 4.4 وحدة الطلبات والعقود
- أمر شراء بحالات: `draft → awaiting_approval → confirmed → in_production → shipped → delivered → closed`.
- شروط الدفع: دفعة مقدمة %، آجل N يوم، دفعات مجدولة (Milestones).
- عقد PDF مولّد آلياً + توقيع إلكتروني.
- النزاعات والمرتجعات (Returns / Credit Notes) مرتبطة بقيود عكسية.

### 4.5 وحدة الشحن واللوجستيات
- شركات شحن متعددة، أسعار شحن بالوزن/الحجم/المنطقة (Incoterms: EXW, FOB, CIF, DDP).
- تتبع الشحنة ورفع مستندات الشحن (Bill of Lading, Packing List, Invoice).
- تحديد الموقع على الخريطة للمورد/المستودع.

### 4.6 وحدة التواصل
- محادثة فورية (WebSockets / Laravel Reverb) مرتبطة بسياق (RFQ / PO / Invoice).
- مرفقات مع فحص أمني، ترجمة فورية اختيارية للرسائل.
- الإشعارات: داخل التطبيق + بريد + Push (FCM) + WhatsApp/SMS للأحداث الحرجة.

### 4.7 وحدة المحاسبة
> موصوفة بالكامل في [وثيقة النظام المحاسبي](02-accounting-system.md).

### 4.8 لوحة Super Admin
- لوحة KPI حيّة: GMV، عدد الطلبات، الإيراد من العمولات، معدل التحويل RFQ→PO، الموردون النشطون.
- اعتماد الموردين، إدارة الاشتراكات والخطط، إدارة العمولات.
- **مركز مالي**: التسويات المستحقة للموردين، المدفوعات، القوائم المالية للمنصة.
- سجل تدقيق كامل (Audit Log) لكل عملية حسّاسة.

## 5. المعمارية التقنية

### 5.1 المكدّس التقني (Stack)

| الطبقة | التقنية | المبرر |
|---|---|---|
| Backend | **Laravel 11 (PHP 8.3)** | نضج، سرعة تطوير، Ecosystem غني، مناسب للأنظمة المالية |
| API | REST + **Laravel Sanctum** | بساطة ووضوح؛ مع إمكانية GraphQL لاحقاً للجوال |
| Frontend Web | **React 18 + TypeScript + Vite** | مكوّنات قابلة لإعادة الاستخدام، أداء عالٍ |
| UI Kit | TailwindCSS + shadcn/ui | تصميم موحّد + دعم RTL كامل |
| Database | **MySQL 8 / MariaDB** | معاملات ACID — شرط لا تنازل عنه للمحاسبة |
| Cache / Queue | **Redis** | الكاش، الطوابير، الجلسات، أقفال التزامن |
| Realtime | **Laravel Reverb** (WebSockets) | بديل مفتوح المصدر لـ Pusher، تحكم كامل |
| Search | **Meilisearch** | بحث عربي سريع مع تحمّل الأخطاء الإملائية |
| Storage | S3-Compatible (MinIO / Wasabi) | ملفات، مستندات، فواتير PDF |
| Mobile | **React Native (Expo)** | كود مشترك iOS/Android |
| Jobs | Laravel Horizon | مراقبة الطوابير والمهام المجدولة |
| Observability | Sentry + Laravel Telescope + Grafana | رصد الأخطاء والأداء |

### 5.2 مبادئ المعمارية

1. **Modular Monolith** في المرحلة الأولى — مجلدات مستقلة لكل Domain (`Catalog`, `RFQ`, `Orders`, `Accounting`, `Payments`) بحدود واضحة، قابلة للفصل لاحقاً إلى خدمات.
2. **Event-Driven داخلياً:** كل حدث تجاري (`InvoiceIssued`, `PaymentReceived`, `OrderDelivered`) يُطلق Event، ووحدة المحاسبة تستمع وتولّد القيد. هذا يفصل منطق الأعمال عن منطق المحاسبة تماماً.
3. **Immutability المالية:** لا تُحدّث القيود المرحّلة ولا تُحذف — التصحيح بقيد عكسي فقط.
4. **Idempotency:** كل عملية مالية تحمل مفتاح تفرّد يمنع الازدواج عند إعادة المحاولة.
5. **Multi-Tenancy:** قاعدة بيانات واحدة + `tenant_id` + Global Scopes + فهارس مركّبة.
6. **Multi-Currency & Multi-Language:** العربية/الإنجليزية (RTL/LTR) من اليوم الأول.

### 5.3 البنية التحتية والنشر

```
[Cloudflare CDN/WAF]
        │
   [Load Balancer]
        ├── App Server 1 (Nginx + PHP-FPM)
        ├── App Server 2
        ├── Queue Workers (Horizon)
        └── Reverb WebSocket Server
                │
        [MySQL Primary] ──> [MySQL Replica (للتقارير)]
        [Redis Cluster]
        [S3 Object Storage]
```
- بيئات: `local → staging → production`.
- CI/CD عبر GitHub Actions: اختبارات → تحليل ساكن (PHPStan L8) → نشر بدون توقف (Zero-downtime via Deployer).
- نسخ احتياطي: يومي كامل + Binlog مستمر، واختبار استرجاع شهري إلزامي.

## 6. الأمان والامتثال

| البند | الإجراء |
|---|---|
| المصادقة | 2FA إلزامي للموردين وللأدوار المالية |
| التفويض | Policies على مستوى الموديل + فحص Tenant في كل طلب |
| التشفير | TLS 1.3، تشفير الحقول الحسّاسة (أرقام الحسابات البنكية) |
| المدفوعات | عدم تخزين بيانات البطاقات إطلاقاً — Tokenization من بوابة الدفع |
| التدقيق | Audit Trail غير قابل للتعديل لكل عملية مالية (من، متى، ماذا، IP) |
| الحماية | Rate Limiting، CSRF، فحص المرفقات، سياسة كلمات مرور صارمة |
| الخصوصية | سياسة احتفاظ بالبيانات، حق المحو، سجل الموافقات |
| الامتثال الضريبي | دعم الفوترة الإلكترونية وقابلية الربط مع هيئة الضرائب المحلية |
| فصل المهام | من ينشئ الفاتورة ≠ من يعتمد الدفع (Segregation of Duties) |

## 7. خارطة الطريق التنفيذية

> المدة الإجمالية المقترحة: **24–28 أسبوعاً** (مقابل 8–12 في العرض الأولي — الفرق يعود كلياً إلى النظام المحاسبي والمتطلبات المؤسسية).

### المرحلة 0 — التأسيس (أسبوعان)
- ورش تحليل المتطلبات، تثبيت نطاق v1.
- مخطط قاعدة البيانات الكامل + **دليل الحسابات المعياري**.
- تصميم UI/UX (Figma): 30–40 شاشة أساسية، نظام تصميم RTL.
- تجهيز المستودع، البيئات، CI/CD، هيكل الوحدات.
- **المخرَج:** وثيقة SRS معتمدة + نموذج بيانات + تصاميم معتمدة.

### المرحلة 1 — النواة والهوية (3 أسابيع)
- المصادقة، 2FA، الأدوار والصلاحيات، نظام المستأجرين.
- تسجيل واعتماد الموردين (KYB)، ملفات المشترين.
- لوحة Super Admin الأساسية + سجل التدقيق.
- **المخرَج:** نظام قابل للدخول بأدوار فعلية.

### المرحلة 2 — الكتالوج والبحث (3 أسابيع)
- المنتجات، المتغيّرات، التسعير التدرّجي، التصنيفات.
- البحث والفلترة (Meilisearch)، صفحات الموردين، المقارنة.
- **المخرَج:** سوق قابل للتصفّح.

### المرحلة 3 — RFQ والتفاوض (3 أسابيع)
- دورة RFQ كاملة، عروض الأسعار، التفاوض، المقارنة، القبول.
- المحادثة الفورية والإشعارات.
- **المخرَج:** دورة التفاوض تعمل طرفاً لطرف.

### المرحلة 4 — الطلبات والشحن (3 أسابيع)
- أوامر الشراء، سير الاعتماد، العقود، الشحن والتتبع، الاستلام، التقييم.
- **المخرَج:** صفقة كاملة من RFQ إلى التسليم.

### المرحلة 5 — المحاسبة: النواة (4 أسابيع) ⭐
- دليل الحسابات، اليومية، الأستاذ العام، محرك القيود الآلي.
- الفواتير وإشعارات الدين/الائتمان، الضرائب.
- الذمم المدينة والدائنة وأعمار الديون.
- **المخرَج:** كل حدث تجاري يولّد قيداً صحيحاً ومتوازناً.

### المرحلة 6 — المحاسبة: المدفوعات والتسويات (3 أسابيع) ⭐
- بوابات الدفع، المحفظة، التحصيل.
- حساب العمولات والاشتراكات، تسويات الموردين (Payouts).
- المطابقة البنكية، المخزون والتكلفة وCOGS.
- **المخرَج:** دورة النقدية والتسوية كاملة.

### المرحلة 7 — التقارير والقوائم المالية (2.5 أسبوع) ⭐
- ميزان المراجعة، قائمة الدخل، المركز المالي، التدفقات النقدية.
- تقارير الضرائب، أعمار الديون، ربحية المنتج/العميل.
- إقفال الفترات والسنة المالية، التصدير (Excel/PDF/CSV).
- **المخرَج:** قوائم مالية معتمدة قابلة للتدقيق.

### المرحلة 8 — تطبيق الجوال (3 أسابيع)
- React Native: التصفّح، RFQ، المحادثة، الطلبات، الإشعارات، لوحة المورد المختصرة.

### المرحلة 9 — الاختبار والتحسين والإطلاق (2.5 أسبوع)
- اختبارات وحدة وتكامل (تغطية ≥ 80% لوحدة المحاسبة — إلزامي).
- **تدقيق محاسبي مستقل** على عيّنة قيود.
- اختبار حمل، اختبار اختراق، تحسين الأداء، SEO.
- تجربة تشغيل مع 5–10 موردين حقيقيين (Pilot)، ثم الإطلاق.

## 9. المخاطر وإجراءات التخفيف

| الخطر | الأثر | التخفيف |
|---|---|---|
| تضخّم النطاق (Scope Creep) | عالٍ | تجميد نطاق v1 بوثيقة معتمدة، أي إضافة تذهب لـ v2 |
| أخطاء في منطق القيود | **حرج** | محرك قيود مركزي + اختبارات تلقائية تتحقق من توازن كل قيد + مراجعة محاسب |
| اختلاف الأنظمة الضريبية بين الدول | عالٍ | محرك ضرائب قابل للتهيئة (Tax Engine) وليس نسباً ثابتة في الكود |
| ضعف جودة بيانات الموردين | متوسط | استيراد CSV بقوالب + تحقق آلي + فريق إدخال في مرحلة الإطلاق |
| التزامن في الأرصدة والمخزون | عالٍ | معاملات قاعدة بيانات + أقفال متشائمة على الحسابات والأصناف |
| تبنّي الموردين للمحاسبة | متوسط | بدء بسيط (فواتير + أرباح) وإخفاء التعقيد خلف "وضع متقدم" |

## 10. معايير القبول (Definition of Done)

النظام يُعتبر جاهزاً للإطلاق عند تحقّق التالي:

1. ✅ دورة كاملة: تسجيل مورد → منتج → RFQ → عرض → PO → فاتورة → دفع → شحن → تسليم → **قيود محاسبية متوازنة في دفتري المنصة والمورد**.
2. ✅ ميزان المراجعة متوازن (مدين = دائن) في كل مستأجر وفي كل فترة.
3. ✅ القوائم المالية الثلاث تُولَّد وتتطابق أرقامها مع الأستاذ العام.
4. ✅ تسوية مورد واحدة تُنفَّذ من الاستحقاق حتى التحويل مع قيودها.
5. ✅ تغطية اختبارات ≥ 80% لوحدة المحاسبة، و≥ 60% عموماً.
6. ✅ زمن استجابة P95 < 400ms للصفحات الأساسية.
7. ✅ اجتياز اختبار الاختراق دون ثغرات حرجة أو عالية.
8. ✅ دعم RTL كامل ولغتان، وتطبيق جوال منشور على المتجرين.

## 11. السياق السوري وملاحظات التكييف

السوق المستهدف (مستوردون سوريون ↔ تجار جملة محليون) يفرض تكييفات واقعية:

| البند | الواقع | التكييف في النظام |
|---|---|---|
| بوابات الدفع الإلكتروني | غير متاحة عملياً | **وضع التحصيل اليدوي**: الدفع يتم بين الطرفين خارج المنصة (نقداً/حوالة)، والمنصة تسجّل الصفقة وتصدر فاتورة العمولة على المستورد. راجع [02 §11.3](02-accounting-system.md) |
| العملة | ليرة سورية + تسعير بالدولار | العملات المتعددة مفعّلة من اليوم الأول، سعر صرف يومي بإدخال يدوي |
| تقلّب الأسعار | يومي وأحياناً أسرع | صلاحية عرض السعر **بالساعات** لا بالأيام، مع تنبيه انتهاء الصلاحية وإعادة تسعير بنقرة |
| جودة الإنترنت | متقطّعة | التطبيق يعمل offline-first للتصفّح، ويزامن عند عودة الاتصال |
| الثقة بين الأطراف | منخفضة | التحقق من السجل التجاري إلزامي + التقييمات + عدّاد الصفقات المكتملة + شارات |
| الشحن الداخلي | شركات محلية صغيرة بلا API | شركات الشحن قائمة قابلة للإدارة يدوياً، والتتبّع بإدخال يدوي للحالة |
| الفوترة الضريبية | متطلبات متغيّرة | محرك الضرائب قابل للتهيئة؛ يمكن تعطيل الضريبة كلياً لمستأجر معيّن |

> **ملاحظة صريحة:** بنية الدفع الإلكتروني والمحفظة والتسويات الآلية مبنية في النظام وجاهزة، لكنها تبقى **معطّلة بإعداد** حتى تتوفر بوابة دفع. تفعيلها لاحقاً تهيئة لا إعادة بناء.
